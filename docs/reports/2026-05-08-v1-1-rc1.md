## Architectural deviation from the roadmap

The roadmap called for **DuckDB attached to SQLite via `ATTACH 'litemlflow.db' AS lmf`**.
We dropped DuckDB after audit:

- DuckDB's Go bindings (`marcboeker/go-duckdb`) require CGO.
- Project's foundational decision is "single binary, no CGO" (uses `modernc.org/sqlite`).
- Adding CGO breaks every distribution channel that depends on the no-CGO promise:
  Homebrew bottle build, Docker `gcr.io/distroless/static`, Snap, Helm chart's
  StatefulSet, K8s operator's `livenessProbe`-friendly distroless image.

Pure-SQLite path that hit the budget instead:

1. **Materialised view `metrics_latest`** maintained via SQL triggers — one row
   per (run_id, metric_key), 100k rows for 100k runs (vs. potentially millions
   in `metrics` for runs with many steps).
2. **Composite index `(key, value DESC, run_id)`** so "top metric across runs"
   becomes an index range scan.
3. **Two-step execution** for max/min: GROUP BY scan to get the aggregate +
   row count, then ONE indexed `LIMIT 1` lookup per group to resolve the
   representative run id. Costs O(N) + O(K) where K = result groups (capped
   at q.Limit).

The window-function approach (single pass with `ROW_NUMBER() OVER` + `COUNT() OVER`)
was tried first and ran at ~417–819 ms because SQLite materialised the
filtered partition in temp B-tree memory. The two-step approach was 3-5x faster.

## Security posture

The DSL is templated, never raw SQL:
- Every value bound via `?` placeholder.
- Every shape choice (agg, group-by family, order direction, lifecycle filter) dispatched through a `switch` over an enum allowlist.
- Group-by suffix `params.<key>` / `tags.<key>`: the `<key>` part is bound, not concatenated.
- 1000-element cap on `experiment_ids[]`, 16-cap on `status[]` — defence against payload DoS.
- Test `TestAnalyticsQueryEnd2End` includes a malicious-metric payload (`eval/f1' OR 1=1; DROP TABLE metrics; --`) confirming the binding path is safe.
