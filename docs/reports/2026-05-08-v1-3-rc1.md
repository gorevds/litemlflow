# v1.3.0-rc1 — Federated multi-server

Release date: 2026-05-08
Roadmap target: docs/roadmap-y2.md → Q3 Y2

## Headline

> 3 LiteMLflow instances behind a single UI; searching `model = gpt-4o-mini` returns experiments from all three.

Acceptance test: `internal/server/federation_http_test.go::TestFederationAcceptance` — 3 nodes (A/B/C),
mutual peer registration, MLflow experiment-create on each, then a single
`GET /api/v1/search?q=fed-shared&federated=1` against A returns origin-tagged
hits from `lmf-A`, `lmf-B`, `lmf-C`.

## What shipped

### Backend

- New `internal/federation` package: HMAC-SHA256 sign/verify (canonical
  `method\npath\nts\nbody`), bounded-FIFO TTL cache (default 256 entries × 30s),
  context-aware `Client.DoCtx` capped at 8 MiB per peer response.
- Migration `012_peers.sql`: `peers(id, name, url, secret, workspace_id,
  added_at, last_seen, status, last_error)` with `UNIQUE(workspace_id, name)`.
- Store CRUD: `CreatePeer`, `ListPeers`, `GetPeer`, `GetPeerByName`,
  `DeletePeer`, `UpdatePeerStatus`. NopStore stubs for tests.
- Native API:
  - `POST/GET/DELETE /api/v1/federate/peers` — operator CRUD.
  - `POST /api/v1/federate/peers/{id}/echo` — connectivity probe.
  - `POST /api/v1/federate/echo`, `POST /api/v1/federate/search` — peer-callable,
    HMAC-validated, exempted from session auth in middleware (HMAC IS the auth).
- `GET /api/v1/search?federated=1` fans out in parallel, dedupes nothing
  (v1.4 backlog), tags every hit with its origin instance, returns
  `{federated, instances, partial}`.
- Config: `LITEMLFLOW_FEDERATION_NAME` (defaults to `lmf-self`),
  `LITEMLFLOW_ENABLE_MULTI_TENANT`. `overlay()` now propagates both.

### UI

- `#/federation` page: peer table (status pill, last-seen, last-error),
  add-peer modal with one-time-secret reveal + clipboard copy, echo + remove.
- Cmd+K palette: "Federated" checkbox (preference persisted), origin pill
  next to remote hits, partial-fan-out warning row when peers fail.
- Favicon (rising-metric-line SVG) — drive-by, separate commit.

## Operator notes

- The first `LITEMLFLOW_FEDERATION_NAME` you set on a node is what other peers
  must register it as. Changing it mid-flight breaks existing peer rows on the
  remote side (HMAC peer name no longer matches).
- Secrets are shown ONCE in the AddPeer response. Lost ones must be rotated by
  removing the row on both sides and re-adding.
- Federation is workspace-scoped — a peer registered under workspace `team-A`
  cannot answer queries for workspace `team-B`. In v1.3 the outbound client
  always queries the peer's `default` workspace; cross-workspace propagation is
  v1.4 work.
